# Список проблем и ограничений

Аудит плагина `opencode-windows-scheduler` v1.1.0, 13.11.2026.
Проверялось поведение инструментов агента, скилла, обёрток запуска и планировщика Windows. После итерации исправлений агенту доступны 22 инструмента.

Статусы:

- **fixed** — исправлено в этой итерации (сборка + тесты прилагаются);
- **open** — известное ограничение, код в этой итерации не менялся.

## 1. `run_task_now` не запускает задачу вне окна расписания — fixed

**Симптом.** Задача с cron `0 4 1 1 *` создаётся, `run_task_now` возвращает `success: true`, но лог остаётся 0 байт, записи в истории нет.

**Причина.** Обёртка задачи всегда вызывает `schedule-gate.js`. Гейт возвращает код 3, если cron не совпадает с текущим временем, а `.cmd`-обёртка трактует код 3 как «не сейчас» и выходит с кодом 0. Для планировщика это выглядит как успешный запуск, поэтому инструмент рапортует успех.

**Исправление.** Одноразовый маркер «ручной запуск»:

- `src/core/schedule-gate.ts` — новый аргумент `--force-file <path>`; свежий маркер (не старше 2 минут) пропускает проверку cron и удаляется, просроченный игнорируется и тоже удаляется.
- `src/core/ps-wrapper.ts` — `requestImmediateRun(name)` создаёт маркер `<lock>.force`; путь передаётся в обёртку через `--force-file`.
- `src/core/wrappers/bash.ts` — то же для POSIX-обёртки (`SCHEDULE_FORCE_FILE`).
- `src/index.ts` — `runTaskEntry()` (общий вход для `run_task_now`, RPC, файловых триггеров, MCP-событий и catch-up) ставит маркер перед `scheduler.runTask()`; при ошибке запуска маркер удаляется.

**Проверка.** `test-schedule-v2.mjs`: свежий маркер при несовпадающем cron → exit 0 и маркер удалён; маркер старше 2 минут → exit 3 и маркер удалён. Плюс проверка наличия `--force-file` в собранной обёртке в `test-agent-tools.mjs`.

## 2. Файловые триггеры включаются только после перезапуска — fixed

**Симптом.** Задача с `triggerType: "file"` и `watchPath` создана, файл изменён — запуска нет, лог пуст. После перезапуска OpenCode триггер работает.

**Причины (две).**

1. `FileWatchManager.refresh()` вызывался ровно один раз при старте плагина; создание/обновление/удаление задачи не пересобирали набор watcher-ов.
2. В схеме `schedule_task` не было поля `watchPath` (оно было только у `update_task`), поэтому file-триггер нельзя было настроить одним вызовом.

**Исправление.**

- `src/index.ts` — менеджер watcher-ов вынесен на уровень модуля; `refreshFileTriggers()` вызывается после успешного создания задачи, после обновления и после удаления.
- `src/index.ts` — в `scheduleTaskSchema` добавлено `watchPath`, значение передаётся в `schedulerCreateTask` (12-й позиционный аргумент).

**Проверка.** `test-agent-tools.mjs`: схема `schedule_task` принимает `watchPath` и сохраняет его. Логика watcher-а покрыта существующими тестами; для полной проверки требуется перезапуск OpenCode (плагин загружается из `dist` при старте).

## 3. `list_tasks` не видит задачи, оставшиеся только в БД — fixed

**Симптом.** В `tasks` есть определения (`gui`, `проверка-статуса-...`), в Планировщике Windows их нет. `list_tasks` отвечает «Задачи плагина не найдены», при этом `dry_run` и `get_history` эти задачи видят.

**Причина.** `collectTasksView()` строил список только из `scheduler.listTasks()` и подмешивал определения по имени. Определения без задачи в ОС в результат не попадали.

**Исправление.** `src/index.ts`: к задачам ОС добавлены определения из БД, которых нет в планировщике. Такие записи помечаются `orphaned: true`, сохраняют расписание/промпт/историю и остаются доступны для `update_task`/`delete_task`.

**Проверка.** `npm run build` + полный `npm test`. Живьём: после перезапуска плагина две «осиротевшие» записи должны появиться в `list_tasks` с `orphaned: true`.

## 4. `delete_task` подтверждает удаление несуществующей задачи — fixed

**Симптом.** `delete_task({ name: "__nonexistent__" })` → `success: true, "Задача ... успешно удалена."`

**Причина.** `deleteTaskWithFamily()` всегда возвращал пустой список удалённых и не проверял существование задачи.

**Исправление.** `src/index.ts`: функция возвращает `{ removed, existed }`; существование проверяется по БД, по задачам ОС и по клонам матрицы. Если задачи не было — `success: false` с текстом `Задача "<name>" не найдена — удалять нечего.`

**Проверка.** Полный `npm test`; поведение проверяется вручную после перезапуска плагина.

## 5. Ограничения инструментов не применяются — open

`allowedTools`/`deniedTools` сохраняются в определении задачи, попадают в обёртку и историю, но `opencode run` v2.2.3 не поддерживает флаги разрешения/запрета инструментов (есть только `--agent`). Фактически это метаданные и подсказка для агента, а не песочница.

**Что делать.** Ждать поддержки в `opencode run` либо запускать задачи через отдельного агента с собственными правами. До этого не полагаться на эти поля как на защиту.

## 6. Часть возможностей доступна только в GUI/RPC — fixed

Агенту не были отданы метрики, настройки, шаблоны, экспорт/импорт, уведомления, дашборд и профили. Теперь это отдельные инструменты с теми же операциями, что у RPC:

- `get_metrics`, `get_analytics` — аналитика запусков и стоимости;
- `manage_settings` — `maxConcurrent`, `winterMode`, уведомления, retention (get/update, частичное слияние);
- `manage_templates` — список, сохранение и удаление шаблонов;
- `manage_profiles` — список, создание, переключение и удаление профилей;
- `transfer_tasks` — экспорт и импорт задач;
- `send_notification` — тестовое уведомление и дайджест;
- `get_dashboard_info` — порт/URL дашборда, платформа, активный профиль;
- `cleanup_history` — очистка истории по возрасту и/или лимиту;
- `emit_event` — запуск задач по MCP-событию;
- `matrix_control` получил действие `preview`.

Итого 22 инструмента агента. Проверены живыми вызовами: чтение метрик/аналитики/настроек/шаблонов/профилей, обновление настроек, round-trip шаблона и профиля, экспорт, предпросмотр матрицы, очистка истории, `emit_event` с несуществующим событием.

## 7. Запуск зависит от сеанса пользователя и питания — open

Задачи регистрируются с `LogonType InteractiveToken`, а также `DisallowStartIfOnBatteries` и `StopIfGoingOnBatteries`. Следствия:

- задача не выполнится, если пользователь не вошёл в систему;
- на ноутбуке от батареи запуск может быть пропущен или остановлен.

Обходной путь: запускать от имени SYSTEM/сервисной учётной записи (требует прав администратора) либо отключить ограничения питания в свойствах задачи. Плагин эти флаги пока не настраивает.

## 8. Одинаковые счётчики запусков у всех задач — fixed

**Симптом.** У задач `gui` и `проверка-статуса-10-утра` одинаковая строка «📊 Всего: 201 | ✅ 130 | ❌ 71».

**Причина.** В `src/gui.tsx` карточка задачи рендерила глобальный сигнал `metrics()`, который заполняется из RPC `get_metrics({})` — суммарные метрики по всем задачам. Локальные счётчики задачи вообще не передавались в GUI.

**Исправление.**

- `src/index.ts` — `collectTasksView()` добавляет к каждой задаче `runsTotal` / `runsSuccess` / `runsError`. Источник — таблица `metrics` (накопительные итоги, не зависят от retention); если строки метрик ещё нет, счётчики считаются по загруженной истории.
- `src/gui.tsx` — карточка показывает `job.runsTotal` / `runsSuccess` / `runsError`; общие метрики вынесены в шапку панели отдельной строкой «Всего по всем задачам».
- Попутно: `fetchHistory()` теперь передаёт `taskName` в RPC, а `GetHistoryInput` (`src/rpc.ts`) и обработчик RPC поддерживают фильтр — окно истории показывает записи только выбранной задачи, а не последние 10 по всем.

**Проверка.** `npm run build`, `npm run build:gui`, `npm test` — без ошибок. Для задачи `gui` ожидаемые значения: 191 / 123 / 68; для `проверка-статуса-10-утра`: 2 / 1 / 1 (по текущей БД).

## 9. Кнопка «Создать» в профилях не реагирует — fixed

**Симптом.** В панели «Профили» нажатие «+ Создать» не открывает ввод и не показывает ошибку — «ничего не происходит».

**Причина.** `handleCreateProfile()` получал имя через `window.prompt(...)`. OpenCode Desktop работает в Electron, где `window.prompt` не реализован и возвращает `null`, поэтому функция молча выходила по `if (!name) return`. Та же проблема была во всех остальных вызовах `window.prompt` (env workspace, добавление/редактирование workspace, имя шаблона).

**Исправление.** В `src/gui.tsx` добавлен собственный модальный ввод:

- `askText(title, initial)` — промис, который показывает модалку с полем ввода; Enter/ОК подтверждает, Escape/«Отмена»/клик по фону возвращает `null`;
- для многострочного env-редактора — `textarea`, Ctrl+Enter сохраняет;
- все 7 вызовов `window.prompt` заменены на `await askText(...)`.

**Проверка.** `npm run build` + `npm run build:gui` (бандл `gui-experimental.cjs` пересобран, 147 КБ), `npm test` — 17/17 сюит проходят. Живая проверка клика — после перезапуска OpenCode (GUI-бандл загружается при старте).
